# 多隔离实例

> 状态：active（最后核对 2026-11-08）

## 2026-11-07 固定显示顺序与彻底删除

当前以[排序与删除合同](2026-11-07-workspace-order-and-deletion.md)为准：Tab 固定按 A-E 排序，用户选择只改变 preferred。状态回执不再写 preferred。标签栏垃圾桶经确认永久删除当前空间配置、运行记录、隔离会话/桌面数据与该空间请求档案；先停止该空间所有活动 App/CLI。其它空间及共享渠道保留。允许删除最后一个，空状态跨重启保留；新增可创建空空间并复用最小空槽位。部分失败保留删除意图，禁止启动/编辑并允许重试。

旧版“方案只软删除”不适用于新入口；下文历史 schema 回退描述不能用来撤销用户已经确认的物理删除。

## 2026-11-06 0.1.7 产品决策：固定五个隔离空间

0.1.7 同时包含工作区可见性恢复和多隔离空间首版。多实例不再允许用户自定义名称；首页把当前「独立隔离空间」标题改成固定标签栏，标签依次为「隔离空间 A」到「隔离空间 E」，最多保留 5 条未删除的 `managed_app` 启动方案。

- 现有未删除的受管理启动方案保留原 `launch_preset_id`、运行实例、隔离 `CODEX_HOME`、Electron 数据和会话库；发布升级只把显示名规范化为已占用的固定槽位名称，不复制、不重建、不删除旧方案。
- 固定名称是持久化显示名，不按当前数组下标实时生成。删除某个空间后，新建空间可以复用最小空闲字母槽位；已有空间的字母不会因删除或排序改变。
- Provider 定义、API Key、探针结果和模型目录属于全局模型渠道库；每个空间独立保存已加入的 Provider 顺序、模型选择、默认模型、API 登录渠道和自动审核模型。一个空间加入或移除渠道不会改变其它空间的绑定。
- 「新增隔离空间」创建空空间（无渠道、无模型、无 API 登录渠道），由用户自行添加；后端将空方案标记为 `needs_model_selection`，选好前不可启动。（2026-11-07 commander 调整，替换此前「复制当前选中空间配置」的合同：新空间不再默认带上当前空间的渠道。）创建不再传 `source_preset_id`——它会继承源空间 profile_options 的登录渠道回填，空方案会报 `login_provider_not_in_workspace`。
- 达到 5 个未删除空间时，新增入口置灰并说明已达到上限；后端也必须返回稳定错误 `managed_app_limit_reached`，不能只依赖 UI 限制。
- 旧版 0.1.6 的数据库可被 0.1.7 读取。首版沿用 schema v21/v23 的表和 `name` 字段，不新增会阻断旧版回退的 schema 版本；槽位由服务层在事务中分配并写入固定名称。

### 0.1.7 验收门槛

- 旧安装升级后，原空间仍显示为「隔离空间 A」，原 preset/instance/home/会话路径和运行绑定保持不变。
- 可以依次创建 B、C、D、E；第 6 次创建在 UI 和后端都失败，已有五个空间不被修改。
- 在 A 中加入渠道或模型，B 的渠道、模型、登录渠道和默认模型不变；反向操作同样成立。Provider 详情和 API Key 仍来自全局渠道库。
- 切换标签只改变当前编辑和启动对象；实例详情、请求记录、打开隔离目录、启动/停止均按当前 preset 精确过滤。
- 新增空间不携带渠道、模型和登录渠道；删除一个空间后，其余空间的名称、目录和运行实例不变，新建空间只复用空闲字母。
- macOS 与 Windows 都完成升级后旧空间恢复、双空间同时启动、单空间停止不影响其它空间的实机验收。

## 目标

用户可以在首页标签栏保留多个隔离实例。每个实例是一条 managed_app 启动方案：空间绑定和模型选择独立保存，首次启动后拥有自己的 CODEX_HOME、会话和 Electron 桌面数据目录。Provider 定义和凭据属于全局模型渠道库。多个受管理 Codex App 可以同时运行。

## 范围

- 首页标签列出全部未删除的 managed_app 启动方案。
- 「新增实例」可点，创建空空间（2026-11-07 起，不再复制当前实例的渠道、模型和 API 登录渠道），名称使用固定槽位「隔离空间 A」到「隔离空间 E」。
- 点标签切换当前编辑/启动对象；选中项写入 is_preferred，刷新后仍停留在该项。
- 编辑渠道和模型时带上当前实例 ID，不再把名称写回固定的「R Codex」。

## 非目标

- 同一条实例已经在运行时，不能再次启动这一条；该操作仍返回 managed_app_in_use。
- 首版最多显示 5 个空间；达到上限时新增入口禁用。
- 不改变 Gateway 回环、凭据库和官方账户关闭合同。

## 合同

- Schema v21 删除 launch_presets_entry_kind 唯一索引，允许多条 entry_kind='managed_app' 记录。
- create_managed_launch_preset：
  - 默认仍更新当前选中（is_preferred）的 managed_app 方案，兼容旧客户端。
  - launchPresetId 更新指定方案。
  - createNew: true 插入新的空方案（2026-11-07 起前端不传渠道与 source），并把它标为 preferred。
- select_managed_launch_preset 只切换 preferred，不增加 version，不改渠道和模型。
- 每个启动方案仍最多绑定一个受管理 App 运行时；CODEX_HOME 在该方案首次启动时分配。
- 写入仍走 ManagedLaunchStore::create_preset / select_preset，UI 不直接写库。

## 验收

- 现有「更新单个主工作区」测试继续通过。
- 新测试：createNew 插入第二条 managed_app 方案；v21 后唯一索引不存在。
- 前端类型检查通过。未启动 Tauri 开发窗口。
- 实机：新增实例后出现固定 Tab，空间绑定从当前实例复制，两个空间可以同时启动。

## 回滚

恢复 schema 版本 20、create_preset 的单方案 upsert，以及首页禁用「新建空间」。已创建的额外 managed_app 行不会自动删除。
