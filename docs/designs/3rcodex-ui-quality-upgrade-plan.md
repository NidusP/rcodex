## 2026-10-04 Gateway 标题状态语义（已实现并验证）

### 目标与范围

标题栏和实例状态摘要区分 Gateway 服务可用和请求活动：服务正在运行但没有处理模型请求时显示「空闲中」；至少一个已准入的模型请求正在由 Gateway 处理时显示「转发中」。Gateway 停止或不可用时沿用现有对应状态。范围限于状态数据、产品文案/图标和状态验证。

### 非目标

不改变 Gateway、实例或绑定的生命周期，不因空闲自动停止服务，不改变路由、准入、重试和凭据行为，也不增加请求正文或凭据采集。

### 用户可见语义

建议将「转发中」定义为 Gateway 正在处理至少一个已准入的模型请求；流式请求持续到完成、失败、取消或超时才算结束。「空闲中」表示服务仍可用，但当前没有在途请求。`activeBindings` 表示已注册的活动路由，不代表请求正在转发；即使隔离实例仍运行且绑定有效，只要没有在途请求，标题栏也应显示「空闲中」。实现需使用 Gateway 的在途请求计数或等价信号，不能用绑定数推断。

### 验收

- Gateway 停止、不可用、运行空闲、单请求转发分别显示准确状态；文字、图标和颜色一致。
- 有活动绑定但没有请求时显示「空闲中」；请求开始后显示「转发中」，完成、失败、取消及超时后恢复「空闲中」。
- 并发请求期间，只要仍有一个请求在途就显示「转发中」；最后一个请求结束后显示「空闲中」。
- 状态刷新或采集失败时不伪报「转发中」，并保留明确的 Gateway 可用性状态。

### 实现与验证记录（2026-10-05）

- `ManagedGatewayStatus`、sidecar 状态和 Tauri `GatewayStatus` 增加 `in_flight_requests`/`inFlightRequests`。计数只在准入、精确路由、能力和 Provider 校验通过且即将访问上游时增加；本地拒绝、健康检查、`/models` 和控制请求不计入。
- 响应 body 由 RAII guard（资源生命周期守卫）持有计数，覆盖普通响应、SSE 流、EOF、上游错误、超时、客户端取消和提前丢弃；`activeBindings` 继续只表示实例绑定，不用于推断对话活动。旧 sidecar 缺少字段时按 0 兼容，可能短暂低报活动状态，升级 sidecar 后消除该限制。
- 前端增加 1 秒 best-effort `gateway_status` 轮询；`serving + 0` 显示「Gateway 空闲中」且状态点静止，`serving + >0` 显示「Gateway 转发中」且状态点脉冲，停止/不可用保持原状态。
- 标题栏、隔离 App 状态条和实例列表的 Gateway 摘要共用同一状态函数；直连 Provider 仍显示为直连，不套用 Gateway 文案。
- 验证：`cargo fmt --all -- --check`、`cargo check --all-targets`、`cargo test managed_gateway::tests -- --nocapture`（43 passed）、`pnpm run check`、`pnpm run build` 均通过。构建仅保留既有 Vite chunk-size 和 connectivity 未使用代码警告；未启动或重启 Tauri 开发服务，未发送真实 Provider 请求。

### 风险与验证

当前 `activeBindings` 不能满足请求活动语义；若没有现成的在途请求信号，需为 Gateway 状态增加轻量计数，并覆盖所有请求退出路径，避免取消、异常或超时后计数泄漏。用无敏感 fixture 验证上述状态和并发转换，再运行 `pnpm run check`、`pnpm run build`，并在真实 UI 中核对空闲与转发显示；不发送真实 Provider 请求作为默认验证。

## 2026-09-24 交互切片

### 目标

打开后能直接看到本机 Gateway、已加入渠道、默认模型、API 登录渠道和活动实例。渠道行能扫到健康、用量和下一步。模型渠道、实例、诊断可以来回切换，添加、编辑和危险确认仍用抽屉或对话框。

### 范围

- 工作区状态条、渠道行、加入确认、启动不可用原因、活动实例时改为查看实例。
- 「更多」收纳打开隔离目录、同步设置、打开默认 Codex、导入项目会话。
- 实例行先显示类型、时间、目录和 Gateway；修订号折进技术详情。
- 诊断按事件、请求记录、完整档案分页，可按失败、渠道和模型筛选；失败行给出可执行的下一步。
- 直连或从未经过 Gateway 的用量显示「未观测」或「直连未观测」，不显示 0。

### 非目标

- 不改 Tauri 命令、路由写入语义或凭据边界。
- 不提供明文 API Key 查看或复制。
- 不把官方套餐或周/小时配额画到 API Key 渠道上。
- 不恢复默认 App 与隔离 App 双卡片，不把单个渠道切换写成用户原 Codex 配置。

### 验收

- 工作区首屏同时有 Gateway、渠道数、默认模型、API 登录和活动实例。
- 选择未加入渠道后，必须再点确认才写入；另一按钮只打开模型选择，保存前不写入。
- 认证失败的已加入渠道在同一行提供编辑密钥和重新检测。
- 启动图标无文字，hover 为「启动」；不能启动时，原因出现在按钮下方。
- 活动实例锁定时，主图标变为查看实例，不自动停止实例。
- 诊断失败项可以按筛选找到，并带有对应恢复按钮。
- pnpm run check 与 pnpm run build 通过；ui-fixture 覆盖工作区、渠道确认、三个页面和诊断筛选。

## 迁移决策与验收口径

本轮采用“工作区主入口 + 一级管理页面”的结构。工作区负责选择已接入渠道、模型和启动目标；模型渠道页面负责来源管理；启动方案页面负责两个固定入口的配置修订；运行实例页面负责生命周期；诊断页面负责脱敏观测。工作区不再重复呈现 Provider 全量资源表。

“首次用户无需打开 drawer”改为以下可验证口径：用户无需先理解内部页面结构，即可从工作区发现配置入口，并沿一条可见路径完成添加渠道、检测、加入入口和启动。添加/编辑表单仍可在 drawer 中完成；“无需打开 drawer”不再表示所有动作都必须在工作区内完成。

## 状态模型与动作矩阵

UI 使用统一的语义状态，所有页面按同一映射显示文案、图标、颜色、主动作和恢复动作。颜色不能单独表达状态。

| 领域 | 后端状态 | UI 语义 | 主动作 | 恢复/辅助动作 |
| --- | --- | --- | --- | --- |
| Provider | `ready` | 健康 | 加入入口/启动 | 检测、编辑 |
| Provider | `degraded` | 不可用 | 查看问题 | 重新检测、查看模型 |
| Provider | `unreachable` | 无法连接 | 编辑地址 | 重新检测 |
| Provider | `unauthorized` | 认证失败 | 编辑密钥 | 重新检测 |
| Provider | 未配置或凭据库不可用 | 未配置/凭据不可用 | 编辑渠道 | 重新保存、查看原因 |
| Gateway | `stopped` | 未运行 | 启动 Gateway | 查看所需入口 |
| Gateway | `serving` | 服务中 | 查看运行实例 | 停止（无活动绑定时） |
| Gateway | `unavailable` | 不可用 | 查看诊断 | 重试启动、复制错误码 |
| 实例 | `running`/`stopping` | 活动/停止中 | 查看实例 | 重新核验、停止 |
| 实例 | `exited`/`failed`/`orphaned`/`degraded` | 已结束/需核验 | 查看诊断 | 重新核验、按规则删除 |
| 入口或 Provider | 活动实例锁定 | 已锁定 | 查看持有实例 | 实例结束后再编辑或删除 |

启动按钮还必须区分默认 App 兼容路由、受管理 App、CLI、直连 Responses 和 Gateway 转换模式；“启动 Gateway 并打开”“启动 Codex”“查看运行实例”只能在状态矩阵中各自对应一个确定条件。

## 目标

把 3R Codex 做成一个“本地控制面”：用户打开后能立刻回答三个问题——当前使用哪条模型路由、下一步该做什么、出了问题如何恢复。视觉上形成稳定的产品识别，交互上围绕“配置 → 检测 → 启动 → 观察”组织，保留现有 Tauri 命令、Provider/Gateway/启动方案/运行实例边界和密钥安全规则。

- 主界面以运行环境工作区为中心，模型渠道、运行实例、诊断主要通过右侧 utility drawer 打开；新增、编辑和确认流程继续叠加 drawer/dialog。

## 产品风格定案

### 视觉关键词

**Calm Technical Console（冷静的技术控制台）**：中性深墨文字、冷灰工作区、青绿色健康状态、靛蓝执行动作、琥珀风险、珊瑚危险。借鉴 OpenCodex 类产品的“任务优先和少装饰”、CCSwitch 的“配置资源治理”、Cockpit Tools 的“账户/实例状态扫描”，只借鉴信息组织和交互密度，不复制品牌、布局或文案。

### 设计原则

1. 一个区域只保留一个主要动作；配置动作、启动动作、危险动作有明确层级。
2. 状态必须同时由文字、图标和颜色表达；颜色不能单独承担含义。
3. 首屏显示状态和下一步，机制解释进入“技术详情”折叠区。
4. Provider 是可管理资产，工作区是日常启动入口，运行实例是生命周期记录；三者不混成一个列表。
5. 抽屉只承载详情和短流程；完整列表、筛选和比较使用主页面。
6. 所有异步动作都显示 loading、完成结果和失败恢复动作，防止重复提交。

## 信息架构

### 一级导航

左侧固定导航（窄窗口折叠为顶部菜单或底部导航）：

- **工作区**：两个固定运行入口、当前路由、快速启动、最近活动。
- **模型渠道**：Provider 列表、添加/编辑、连通性、模型目录、余额和用量。
- **启动方案**：方案草稿、模型选择、传输方式和“下次启动生效”提示。
- **运行实例**：活动/已结束实例、停止、重新核验、实例诊断。
- **诊断**：Gateway 与请求时间线、错误码、延迟和下一步建议。

顶部栏只放当前 Gateway 状态、刷新、主题和设置。现有工作区的两张运行目标卡保留，作为主要视觉焦点。

### 页面结构

工作区首页建议按以下顺序：

1. Gateway 状态条：当前是否运行、是否为直连模式、一个上下文明确的主按钮。
2. 当前路由摘要：已加入渠道、模型数、传输方式、最近检测时间。
3. 默认 App 与受管理 App 两张运行环境卡：每张卡显示状态、渠道/模型摘要、主 CTA 和次级配置入口。
4. 最近活动：最近启动、最近检测、最近错误三类事件，最多展示 5 条。

最近活动只读取已有的启动、检测和诊断记录，不新增后台采集线程；每项显示时间、对象、结果和可执行下一步。没有记录时使用空状态 CTA。时间统一按本机时区显示，保留原始时间戳供排序，敏感详情遵守诊断脱敏规则。

模型渠道、运行实例、诊断页面使用列表/表格骨架；详情、编辑和确认继续使用右侧 drawer/dialog。

## 设计 Token（第一版）

建议在 `styles.css` 顶部建立语义变量，组件只引用变量，不再直接写颜色字面量。

除颜色外，Token 还必须覆盖 focus ring、z-index 层级、内容最大宽度、图标尺寸、表格密度、滚动条、状态边框和字体字重。P0 完成后增加静态检查，禁止新增颜色字面量；历史样式逐步迁移，不要求一次性重写全部 CSS。

### 颜色

| Token | Light | Dark | 用途 |
| --- | --- | --- | --- |
| `--bg` | `#F4F6F7` | `#11151A` | 应用背景 |
| `--surface` | `#FFFFFF` | `#1A2027` | 卡片、抽屉、弹窗 |
| `--surface-subtle` | `#EEF2F3` | `#202831` | 次级区域、hover |
| `--text` | `#17212B` | `#E7EDF2` | 主文字 |
| `--muted` | `#61717C` | `#9AA8B4` | 辅助文字 |
| `--border` | `#D8E0E4` | `#303B45` | 边框、分隔线 |
| `--primary` | `#3D52C7` | `#8293FF` | 启动、应用、选择 |
| `--brand` | `#137A64` | `#53C7A1` | 品牌、健康、当前 |
| `--info` | `#2A71B8` | `#77B7F0` | 信息、检测中 |
| `--warning` | `#A66A13` | `#E5B35C` | 降级、待处理 |

健康色使用 `--brand`，执行 CTA 使用 `--primary`，避免整页被绿色染色。深色主题只保留一套规则，删除重复和无效的 `.dark html[data-theme]` 选择器。

### 尺寸、圆角和动效

- 间距：`4 / 8 / 12 / 16 / 24 / 32`，主要布局以 8 为基线。
- 控件高度：桌面 36px，紧凑图标按钮 36px；触摸端最小命中区 44px。
- 圆角：控件 8px，卡片 12px，弹窗/抽屉 16px；避免每个元素都做胶囊形。
- 边框 1px；普通卡片只用轻阴影，弹窗使用更高一级阴影。
- 状态变更 160ms，drawer 240ms，dialog 220ms，统一 cubic-bezier；减少动画时只保留显隐和焦点变化。

### 字体

系统无衬线字体作为默认；标题 20/28、区块标题 16/24、正文 14/22、辅助 12/18。按钮、select、输入框和状态栏明确写出字号和字重，不依赖浏览器默认值。

## 组件规范

编码与目录规则以 AGENTS.md「前端与交互规则」为准：功能目录 + `index.ts` 对外导出，React 组件写 `@component` / `@description`。`src/main.tsx` 与 `src/App.tsx` 只做根组装。

视觉层仍沿用下列基础件语义；实现上优先 Mantine，再用控制面 className 覆盖外观，不再新建 `src/ui/` 或原生弹出层。


先做基础层，再迁移页面，组件建议放入 `src/ui/`：

- `Button`：`primary / secondary / ghost / danger / icon`，状态包括 hover、pressed、focus、loading、disabled。
- `Field`：label、required、helper、error、success；错误与输入通过 `aria-describedby` 关联。
- `Select`：统一高度、箭头、键盘操作、空值和禁用态；模型选择器显示来源与模型名。
- `StatusBadge`：`healthy / checking / degraded / failed / locked / direct`，文字+图标+颜色。
- `Card`、`ListRow`、`Table`：统一 padding、边框、选中态和操作区。
- `Drawer`、`Dialog`、`Toast`、`Tooltip`：共用 OverlayManager、z-index、焦点和退出策略。
- `EmptyState`：解释当前状态并提供一个可执行 CTA，例如“添加第一个模型渠道”。
- `TimelineItem`：时间、事件来源、状态、错误码、下一步；错误码支持复制。

`OverlayManager` 负责登记当前打开层、背景隔离、滚动锁、Escape 关闭、焦点陷阱和关闭后的焦点恢复。业务组件只能声明层类型和关闭策略，不能自行设置 z-index 或直接操作全局焦点。异步提交期间禁止通过 Escape、遮罩或重复按钮破坏未完成操作，并必须保留失败后的表单内容。

所有写操作必须携带当前资源版本或等效的预期版本。发生版本冲突时，保留用户草稿、刷新最新快照并显示“已有其他操作更新，请检查后重试”；刷新不得覆盖未提交表单。加载、检测、启动、停止和删除的 busy 状态按资源隔离，单个 Provider 的操作不能锁住整个工作区；超过后端有界超时时，显示重试和诊断入口。

## 关键交互方案

### Provider 添加流程

采用短流程分组，而不是一次展示所有高级字段：

1. **连接**：名称、Base URL、API Key；实时校验并显示密钥只进系统凭据库。
2. **检测**：执行 `/models` 和最小文本请求；显示可用、不可用、认证失败、无法连接。协议未确认属于不可用。
3. **选择模型**：按 Provider 分组选择模型，设置公共显示名和默认模型。
4. **加入工作区**：显示将影响哪个入口，以及“保存后下次启动生效”。

检测失败时，错误旁直接放“编辑密钥”“重新检测”；不要要求用户回到列表寻找恢复动作。

模型目录需要支持以下边界：无模型、目录读取成功但文本检测失败、重复公共模型 ID、已移除 Provider、手工映射和默认模型失效。工作区保存后显示影响的入口和配置修订；活动实例存在时显示锁定原因，并提供跳转实例的动作。

### 启动交互

运行环境卡只保留一个主要 CTA：

- Gateway 必须启动且未运行：`启动 Gateway 并打开`。
- 直连模式：`启动 Codex`。
- 已有活动实例：主按钮变为 `查看运行实例`，配置和删除动作按资源锁定。

启动对话框先选 CLI/App，再填写一次性工作目录；启动前显示路由摘要和凭据边界，避免把技术日志塞进确认层。

### Drawer/Dialog 行为

- 打开后自动聚焦标题或第一个可编辑字段，关闭后恢复到触发按钮。
- 打开期间锁定背景滚动，Tab 只在当前层循环；Escape 关闭最上层。
- 点击遮罩关闭只适用于非破坏性详情 drawer；危险确认必须使用明确按钮。
- drawer 分为 360px（轻详情）、480px（表单）、640px（复杂配置）三档；小于 680px 时变为全屏 sheet。
- 多层 overlay 使用统一堆栈，禁止业务组件自行决定 z-index。

### 诊断呈现

首屏只显示状态、时间、路由、HTTP 状态、耗时和下一步。代理端口、sidecar 路径、请求边界等技术解释放入“技术详情”。错误码可复制，长错误摘要支持展开，不截断关键字。

诊断只允许展示经过白名单处理的字段。错误摘要、上游地址、路径、请求头和复制内容不得包含 API Key、认证 Token、Cookie、URL 查询参数、本机用户名或未截断的敏感路径；每条摘要设最大长度和保留期限。凭据库授权拒绝、超时和不可用必须显示为独立状态，不得表现为普通网络错误。

## 文件和组件拆分

按功能拆分现有单文件，保持业务合同不变。目录约定见 AGENTS.md「前端与交互规则」，不再新建 `src/ui/` 或 `src/features/`：

```text
src/
  App.tsx                      根组装：标题栏、工作区、通知、叠层
  components/title-bar/        窗口标题栏
  components/isolated-app/     独立工作区页面
  components/model-utility/    模型渠道、实例、诊断抽屉
  components/runtime-panels/   启动确认与实例列表
  components/app-state/        共享状态与 Mantine 主题
  components/hinted-button/    按钮
```

第一阶段不要同时改 Rust、Tauri command 或数据模型；UI 层通过现有 `codex-control.ts` 调用后端。

- 活动实例锁定相关操作在行内直接解释。
- 明确列表分页或虚拟化策略，搜索输入防抖，排序字段、时区和诊断保留期限。

验收：使用固定的 100 条脱敏 fixture，在目标设备上按指定条件找到失败项的中位时间不超过 10 秒；列表不依赖逐条展开才能理解状态；清理和加载失败均有明确反馈。

### P4：响应式、主题和质量验收（1 个迭代）

- 320–480px 专项布局；关键文字 CTA 保留，触控命中区至少 44px。
- 深色主题统一为中性深墨，绿色只表示健康/当前。
- 建立 Playwright 截图基线和 reduced-motion 检查。
- 建立 Playwright 脚本、无敏感 fixture 和打包 Tauri 运行时验收；浏览器预览只验证静态 UI 和交互，Provider 持久化、凭据库、Gateway、实例启动必须在打包运行时验证。

验收：320px、390px、768px、1440px 和 200% 缩放无横向溢出；键盘和屏幕阅读器可完成核心流程；正文对比度至少 4.5:1、大字号至少 3:1、非文字控件至少 3:1；截图基线排除时间戳、PID、随机 ID 和环境路径造成的假差异。

## 视觉和交互验收清单

- 首屏是否同时说明当前路由、状态和下一步？
- primary、secondary、ghost、danger 是否一眼可区分？
- button、select、input 是否具备 hover/pressed/focus/loading/disabled/error 状态？
- drawer/dialog 是否自动聚焦、锁定背景、Escape 关闭并恢复焦点？
- 错误是否在发生位置提供恢复动作？
- 状态是否同时有文字、图标和颜色？
- 长说明是否从首屏移入技术详情？
- Provider、启动方案、实例、诊断是否符合各自对象边界？
- 深色主题是否只有一套语义 token？
- 390px 窄窗口是否保持可读、可点、无横向滚动？
- `prefers-reduced-motion` 是否保留状态变化而移除位移动画？
- 不新增后端 secret 展示、日志正文或默认 Codex 接管行为。
- 凭据库授权拒绝、超时、Gateway 启动失败、实例孤儿状态、配置版本冲突是否都有明确恢复路径？
- 默认 App 与受管理 App 的配置、认证、模型目录、实例和停止语义是否在文案中保持区分？
- 200% 缩放、屏幕阅读器、键盘 Tab 顺序和焦点可见性是否通过检查？
- 列表搜索、筛选、排序、分页和清理是否在加载、空结果、失败和恢复后保持上下文？

## 建议衡量指标

- 首次配置完成率：预先定义“主要动作”（打开配置、填写并保存、检测、加入入口、启动），从空状态到成功启动不超过 5 个主要动作；记录分母、失败原因和退出位置。
- 错误恢复率：认证失败和无法连接各使用固定 fixture，统计用户在同一上下文完成重新检测的比例及恢复耗时。
- 首屏理解测试：给出固定状态截图或可运行环境，用户在 10 秒内指出当前状态和主 CTA；记录正确率，不只记录主观反馈。
- 可扫描性：使用 100 条记录和固定失败条件，记录找到目标项的中位时间、最长时间和误点击次数。
- 质量门槛：核心路径零控制台错误、零横向溢出、键盘路径 100% 可完成、截图回归无超过批准阈值的布局漂移。
- 性能门槛：以目标设备和 100 条脱敏 fixture 为基线，首屏状态可交互时间目标不超过 2 秒，列表筛选响应时间目标不超过 100ms，抽屉首帧目标不超过 150ms，诊断列表加载目标不超过 500ms；先记录基线，再按 p95（95% 请求耗时不超过该值）验收。

所有指标应在实现前记录基线、设备、fixture、样本数和通过阈值；没有这些字段的指标只作为观察项，不能作为发布门槛。

## 非目标和风险

- 不在本次 UI 改造中改变 Gateway 路由合同、Provider 数据模型、密钥保存方式或启动隔离策略。
- 不把 3R Codex 做成营销型 dashboard；装饰性渐变、假指标、过度卡片化会降低控制台的可信度。
- 从单文件拆分到 feature 目录会增加短期文件数量；应在 P0 先稳定 token 和组件 API，再逐页迁移，避免业务状态与视觉重构同时失控。

## 发布、迁移与回滚

- 每个阶段保持可构建、可启动、可回退；先迁移 Token 和 UI 状态映射，再迁移页面，不在同一个提交中同时改 Rust、Tauri command（桌面端调用接口）或数据模型。
- 页面入口迁移期间保留旧入口的可达性，直到新页面完成同等功能和打包运行时验收；旧入口和新入口不得各自写入不同的工作区语义。
- 不迁移或复制凭据、默认 App 配置、实例目录和会话数据；只迁移本地 UI 偏好时必须使用字段白名单。
- 发生回归时，回滚粒度应至少覆盖一个完整页面或组件组；回滚不得删除 Provider、工作区修订、诊断或实例记录。
- 方案、实现和验收记录都标注基线版本、验证环境和未覆盖风险；发布前必须重新检查当前实现是否仍符合本文件的“状态与当前实现基线”。
